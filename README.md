# Geant4 Docker Learning Environment

![Geant4](https://img.shields.io/badge/Geant4-Monte%20Carlo-blue) ![Docker](https://img.shields.io/badge/Docker-Enabled-2496ED?logo=docker&logoColor=white) ![C++](https://img.shields.io/badge/C%2B%2B-17-00599C?logo=cplusplus&logoColor=white) ![Status](https://img.shields.io/badge/Status-Learning%20%26%20Research-yellow)

This repository is a **hands-on learning and research environment** for running Geant4 in Docker and exploring particle transport, nuclear interactions, secondary-particle production, and energy deposition in semiconductors.

Starting from Geant4's official Basic Example B1, the repository includes `LunarDevice`, a simulation of proton and neutron irradiation of a silicon chip inside an aluminum enclosure. Two further applications are planned: `LunarSurface`, for secondary neutrons escaping from lunar regolith, and `SpaceCraft`, for secondary neutrons produced by spacecraft structures and shielding.

> **Scope:** This repository is for education, investigation, and prototyping. Its current models are **not validated representations** of the lunar radiation environment, a real spacecraft, or semiconductor single-event upset (SEU) rates. Simulated counts and doses must not be interpreted as real-world rates without appropriate source normalization and validation.

## 1. What Is Geant4?

[Geant4](https://geant4.web.cern.ch/) is a C++ toolkit for Monte Carlo simulation of the passage of particles through matter. Its physics models describe particle transport, ionization, scattering, nuclear interactions, secondary-particle production, and energy deposition. Users define the geometry, materials, particle sources, physics models, and quantities to record.

This repository focuses on a practical question: **Which particles are produced, where are they produced, and where do they go when a particular material is irradiated?**

- **Primary particle:** A particle injected by the source at the beginning of an event, such as a proton or neutron.
- **Secondary particle:** A particle produced by an interaction involving a primary particle or another secondary.
- **Event:** One simulated source event; `/run/beamOn N` executes `N` events.
- **Track / step:** A particle's track and the individual transport or interaction steps along it.
- **Physics list:** A collection of models and processes used for electromagnetic, hadronic, and other interactions.
- **Scoring:** Recording or accumulating quantities such as boundary crossings, deposited energy, and interactions.

## 2. Repository Goals

1. Build and run Geant4 inside Docker, with a manageable and reproducible software environment.
2. Learn by changing geometry, materials, particle sources, and visualization settings.
3. Use `LunarDevice` to study irradiation of an aluminum enclosure and silicon chip, including nuclear interactions and secondary-particle generation.
4. Develop `LunarSurface` to examine upward-leaking secondary neutrons from lunar regolith, and `SpaceCraft` to examine secondary neutrons generated by spacecraft materials and reaching internal components.
5. Progress from simple monoenergetic, unidirectional sources toward GCR particle species, energy spectra, and angular distributions, with verification and validation at each stage.

## 4. Requirements

- Docker Engine and Docker Compose.
- Ubuntu/Linux is the primary target; WSL2 may also be used.
- Interactive 3D visualization requires a working display server (such as X11/Wayland) and graphical display forwarding into Docker.
- Sufficient CPU, memory, and disk space, especially for large high-energy particle simulations.

The Docker image is intended to provide Geant4, CMake, compilers, and their dependencies. The precise Geant4 version and available physics datasets depend on the container build.

## 5. Starting the Docker Environment

Run the following commands **on the host**:

```bash
cd ~/projects/geant-learn

docker compose build
docker compose up -d

docker compose config --services   # Find the actual service name
docker compose ps
```

Enter the container using its configured service name:

```bash
docker compose exec <service-name> bash
```

Replace `<service-name>` with a name returned by `docker compose config --services`. Do not attempt to run Docker again if you are already inside the container.

Verify the environment **inside the container**:

```bash
geant4-config --version
ls /home/app/geant4-ws
```

The development environment has used Geant4 11.4.3; verify the version actually installed with the command above.

## 6. Building and Running LunarDevice

The following commands run **inside the container**:

```bash
cd /home/app/geant4-ws/LunarDevice
cmake -S . -B build
cmake --build build -j 4
cd build
./lunar_device
```

Recent versions use `lunar_device` as the executable name. If it does not exist, inspect the build directory and the `add_executable` declaration in `CMakeLists.txt`. If CMake cannot locate Geant4, check the installed `Geant4Config.cmake` and configure `Geant4_DIR` if needed.

### Interactive mode (GUI)

Normally, launch without arguments, inspect the geometry, and issue particle-source and run commands in the Geant4 UI:

```text
/gun/particle proton
/gun/energy 50 MeV
/gun/direction 0 0 -1
/run/beamOn 100
```

To switch to neutrons:

```text
/gun/particle neutron
/gun/energy 50 MeV
/run/beamOn 100
```

These `/gun/...` commands take effect when the application uses `G4ParticleGun` and does not overwrite the values for every event. Check the logs or recorded metadata to verify the actual source settings. The intended interactive behavior is **not** to run `/run/beamOn` automatically at startup.

### Batch mode

Check the macro command-line interface implemented in the current application. A conventional Geant4 B1-style invocation is:

```bash
cd /home/app/geant4-ws/LunarDevice/build
./lunar_device ../run_lunar.mac
```

However, recent versions may support options such as `--macro` and `--target` for batch runs and output management. **Confirm the actual CLI** with `./lunar_device --help` (if supported), the source code, or the application-specific README. Do not assume the obsolete `exampleB1` command still works.

## 7. LunarDevice Simulation Model

The initial learning geometry is:

| Region | Material | Nominal dimensions |
|---|---|---|
| World | Vacuum | 600 × 600 × 600 mm |
| AlCase (outer dimensions) | Aluminum | 100 × 100 × 30 mm |
| Cavity | Vacuum | 96 × 96 × 26 mm |
| Chip | Silicon | 10 × 10 × 0.5 mm |

The aluminum enclosure has a nominal 2 mm wall thickness, and the silicon chip is located near the center. If geometry dimensions are configurable, **runtime configuration takes precedence** over these nominal values.

The original source was a monoenergetic 100 MeV proton beam traveling from +Z toward -Z, with a transverse source area covering the projected chip. The interactive UI is now used to explore different incident particles and energies. **This is not a realistic GCR spectrum.**

The initial physics list was `QBBC`. Studies involving low-energy neutron transport or heavy GCR ions will require further evaluation of physics-list suitability, model energy ranges, and the required nuclear datasets.

## 8. Visualization

Interactive runs can display particle trajectories overlaid on the aluminum enclosure and silicon chip. The `TSG_QT_GLES` driver has been used in development.

Target visualization settings:

| Object / particle | Appearance |
|---|---|
| AlCase | Gray wireframe |
| Chip | Translucent blue, with blue wireframe fallback |
| Proton | Cyan |
| Neutron | Yellow |
| Gamma | Green |
| Electron | Red |
| Positron | Magenta |

Besides particle-identity coloring, an experimental mode can use particle identity for hue and kinetic energy for brightness. Consult `LunarDevice/macros/` and `LunarDevice/README.md` for the exact mode-selection commands in the installed version.

**Stability note:** Segmentation faults have previously occurred in TSG when updating scenes or changing filters. Avoid repeatedly creating viewers, scenes, and trajectory drawing models; restart the application when necessary. Transparency rendering may depend on the driver and host graphics environment.

A visible trajectory alone does not establish which nuclear reaction occurred. Correlate the display with CSV data on interaction positions, processes, and particle parentage.

## 9. Outputs and Interpretation

`LunarDevice` has been extended with CSV logging for simulation analysis. Observed output file families include:

- `events_*.csv`: Event-level records.
- `reactions_*.csv`: Nuclear interaction records, including processes such as `protonInelastic`.
- `neutrons_*.csv`: Neutron-related records.
- `crossings_*.csv`: Geometry boundary crossing records.

A reaction record may contain `run_id`, `event_id`, `track_id`, `parent_id`, `particle`, `process`, `volume`, kinetic energies before and after the interaction, interaction coordinates, and counts of secondaries and neutrons.

**Always inspect the current implementation** for exact CSV schemas, destination directories, overwrite rules, and multithreaded file handling. For comparisons, record the primary particle, energy, direction, geometry, materials, physics list, Geant4 version, random seed, and number of events.

### Useful observables

- **Secondary-neutron yield:** Number of generated neutrons divided by the number of incident primary particles.
- **Boundary-crossing yield:** Number of neutrons crossing a defined surface in a defined direction, divided by the number of incident primaries.
- **Energy and angular distributions:** Evaluated either at production or at a defined scoring boundary.
- **Silicon energy deposition:** Total deposited energy in the selected silicon volume.
- **Absorbed dose:** \(D = E_{\mathrm{dep}}/m\).

**Production counts, boundary crossings, physical flux, and SEU rate are different quantities.** Repeated crossings of the same boundary may be double-counted unless directions and first-crossing rules are specified.

## 10. Planned Applications (Not Yet Implemented)

### LunarSurface — Secondary neutrons from lunar regolith

- Start with a planar regolith layer approximating a semi-infinite medium.
- Verify the basic physics with a monoenergetic, unidirectional proton beam.
- Sweep primary energy, incidence angle, layer thickness, density, composition, and hydrogen content.
- Record upward-going neutron yield, energy spectrum, and angular distribution at the lunar surface.
- Subsequently introduce GCR composition, energy distributions, and zenith-angle distributions.

Here, **albedo neutrons** do not mean only mirror-like reflections. They include neutrons generated and transported inside regolith that eventually escape upward after nuclear interactions and scattering.

### SpaceCraft — Secondary neutrons in spacecraft and shielding

- Start with a single aluminum slab; then add multilayer shielding and box-like structures.
- Sweep materials, areal density, and primary energy.
- Score neutron production inside materials separately from leakage outside the shield and neutron transport into the electronics region.
- Subsequently consider GCR irradiation from multiple directions and more complex structural layouts.

**The material producing the most neutrons is not necessarily the material exposing internal electronics to the greatest hazard.** Comparisons must use a clearly defined and consistent observable.

## 11. Limitations and Reproducibility

- Results depend on nuclear models, especially for low-energy neutron transport and heavy-ion reactions. `QBBC` is not a universal solution.
- For finite regolith layers, assess leakage through the bottom and sides and potential boundary artifacts.
- Monoenergetic beam yields are **not** physical production rates in a GCR environment. A source spectrum, area, time, solid angle, and normalization are required for physical rates.
- Energy deposited in silicon is not itself an SEU or single-event latchup (SEL) probability; charge collection and circuit response require separate models and validation.
- Match or record primary counts, random seeds, physics lists, and statistical uncertainties when comparing configurations.
- Use batch mode for large runs and the GUI for a limited number of events.
- Do not use unvalidated outputs as the sole basis for radiation qualification or mission-critical design decisions.

## 12. Troubleshooting

**`Geant4Config.cmake` not found:** Locate the Geant4 installation in the container and, if needed, pass `Geant4_DIR` to CMake.

**Qt window does not appear:** Check the host display server, `DISPLAY`/Wayland settings, and Docker Compose GUI forwarding. Batch simulation does not require a GUI.

**Macro changes do not take effect:** The build directory may contain stale macro copies. Check CMake's copy rules and the working directory, and reconfigure when necessary.

**Duplicate tracks or unexpected colors:** Check whether multiple trajectory drawing models or scenes were registered. Select one coloring mode at a time.

**Viewer crashes during refresh:** Isolate the issue with a small event count, avoid recreating scenes, and try wireframe rendering. Capture a backtrace if needed.

**Results are overwritten:** Confirm the implemented CLI and output directory rules. Keep disposable exploratory runs separate from runs intended for preservation.
